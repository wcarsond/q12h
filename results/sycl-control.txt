SYCL control: the same Arc silicon, the same models, a different backend
=======================================================================

Why this run exists
-------------------
The Vulkan backend loses 3.7x of throughput when the batch crosses 8 columns
(-ub 8 = 2151 t/s, -ub 9 = 579 t/s on an Arc Pro B60). The obvious objection is
that the hardware simply does not like 9, and that mul_mat_vec_max_cols = 8 is
therefore protecting users from a real limit.

This rules that out. Same GPU, same driver, same models, only the backend
changes. If the cliff were physical it would appear here too.

It does not. Throughput rises monotonically from 8 all the way to 32:

  llama-bench -p 512, Intel Arc Pro B60, SYCL backend

  n_ubatch              8        9       12       16       24       32
  qwen2 1B BF16      611.7    673.9    893.1   1210.1   1601.4   2195.3  t/s
  qwen2 7B Q4_K_M    619.0    655.8    853.2   1123.1   1175.5   1484.2  t/s

  (full llama-bench output below)

So the cliff is a property of the Vulkan backend's dispatch heuristic, not of
the GPU. That is what makes it a bug rather than a hardware limit.

Note on what the SYCL backend is doing underneath: it runs oneDNN and oneMKL,
which this build reports as

  GGML_SYCL_DNNL: yes
  GGML_SYCL_ENABLE_DNN: 1
  GGML_SYCL_FA_ONEDNN: 1
  GGML_SYCL_ENABLE_MKL_FA: 1

That is Intel's own stack for this hardware. It is used here only as a
reference point - all of the work in this repository is on the Vulkan backend,
which is vendor-neutral and therefore where a fix generalizes.
